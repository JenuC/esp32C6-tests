Chapter 7

Reading the header

Stop staring at hex. Everything up to the payload is plain 802.15.4 — identical for Zigbee, Thread and XBee — so parse it once and the sketch can tell you who is talking to whom, and exactly where the payload starts.

Sketch sketches/ch07_parse_header/ch07_parse_header.ino

Little-endian, everywhere

Every multi-byte field in this header is little-endian. The bytes 61 88 on the wire are the 16-bit value 0x8861. Reading them in the wrong order is the single most common mistake when decoding these frames by hand, and it produces a frame type that makes no sense, which at least fails loudly.

The Frame Control Field

Those first two bytes decide the shape of everything after them:

BitsFieldIn 0x8861
0–2Frame type001 — Data
3Security enabled0
4Frame pending0
5ACK request1 — sender wants an ACK
6PAN ID compression1 — source PAN omitted
10–11Destination addressing mode10 — 16-bit short
12–13Frame version0
14–15Source addressing mode10 — 16-bit short

Frame types are 0 beacon, 1 data, 2 acknowledgment, 3 MAC command. Addressing modes are 0 none, 2 short (16-bit), 3 extended (64-bit) — mode 1 is reserved.

Why the header is variable length

Three of those fields change the size of what follows, which is why fixed byte offsets do not work:

FCF              2 bytes, always
sequence number  1 byte, always
dest PAN         2 bytes, if dest mode != none
dest address     2 or 8 bytes, per dest mode
src PAN          2 bytes, ONLY if src mode != none AND NOT pan_compress
src address      2 or 8 bytes, per src mode
payload          whatever is left

PAN ID compression is the one that catches people. When it is set, both endpoints are in the same PAN, so the source PAN ID is simply not transmitted — the header is two bytes shorter than a naive reading expects, and every field after it shifts. A parser that ignores that bit reads the payload starting two bytes early and produces plausible-looking nonsense.

The sketch's parser handles all the combinations and bounds-checks every read against the frame length, so a truncated frame is rejected rather than read off the end.

A worked example

One real frame from the captures in this repository:

61 88FCF
46seq
01 0Bdst PAN
00 00dst addr
01 00src addr
83 00 0Bpayload
C1 0Brssi / lqi

Destination PAN 0x0B01, destination 0x0000, source 0x0001. No source PAN appears because compression is on. What the sketch prints:

len 14  rssi  -63 dBm  lqi  11  | 61 88 46 01 0B 00 00 01 00 83 00 0B C1 0B
    FCF 0x8861  Data, ACK requested, PAN compressed, ver 0
    seq 0x46 (70)
    dst  pan 0x0B01  addr 0x0000
    src  pan 0x0B01 (implied)  addr 0x0001   [short/short addressing]
    payload 3 bytes at offset 9: 83 00 0B
    as text: "..."

Compare an ACK, which carries no addressing fields at all and so is five bytes:

len  5  rssi  -62 dBm  lqi   7  | 02 00 51 C3 07
    FCF 0x0002  Ack, ver 0
    seq 0x51 (81)
    dst  none
    src  none   [none/none addressing]
    payload 0 bytes at offset 3:

Its sequence number matches a data frame sent moments earlier. That is the whole mechanism — an ACK identifies what it is acknowledging by sequence number and nothing else.

The ASCII column

The sketch renders the payload as text as well as hex. When you do not know what a protocol is, this is the fastest possible triage: readable strings mean the payload is text or has text in it, and you are nearly done. All dots means it is binary and packed, and you are headed for chapter 10.

For these monitors it was all dots.

Two bytes short

The parser computes mac_len = psdu_len - 2 because the last two bytes of a received PSDU are not part of the MAC frame. That is the subject of the next chapter, and getting it wrong is how a 3-byte payload looks like a 5-byte one with two fields that never quite make sense.
