Chapter 4

The twenty frame wall

Chapter 3 stopped after exactly 20 frames. Not 20-ish — 20. A suspiciously round number is a clue, and this one points straight at the cause.

Sketch sketches/ch04_buffer_wall/ch04_buffer_wall.ino

Reading the symptom

Three facts, taken together, name the bug before you look at any code:

  • It stops at a round number. Resource exhaustion, not corruption. Random damage does not produce the same count twice.
  • The heartbeat keeps running. The sketch is alive. This is not a crash or a hang, and chapter 2's heartbeat is what rules those out.
  • It never recovers. Whatever ran out is never given back.

Something finite was consumed once per frame and never released. There are exactly 20 of them.

What the pointer actually is

The frame pointer handed to the callback is not yours and it is not a copy. It points into one of a pool of statically allocated receive buffers, sized by CONFIG_IEEE802154_RX_BUFFER_SIZE, which defaults to 20.

Each buffer stays checked out to your code until you hand it back. Chapter 3 never did. After 20 frames the driver had nowhere to put the 21st, and the radio went permanently deaf.

The pool is global

It is not per channel. This is why the scanner in chapter 6, if it leaked, would go silent across all sixteen channels at once rather than just the one it was on — a symptom that sends people hunting for a channel-hopping bug that does not exist.

The fix

One line, at the end of the callback:

esp_ieee802154_receive_handle_done(frame);

Order matters. Release it after you have finished reading frame — once it goes back in the pool the driver may reuse it for the next packet at any moment. Anything you still need must be copied out first, which is exactly the problem chapter 5 solves properly.

If that function does not compile

Your Arduino-ESP32 core predates IDF 5.1. Upgrade to core 3.x. There is no workaround on older cores, because the function that returns a buffer does not exist in them.

Verifying

Flash the chapter 4 sketch and watch the counter walk straight past 20:

[ 20108 ms] alive, frames so far: 47
[ 22110 ms] alive, frames so far: 52
[ 24112 ms] alive, frames so far: 58
A tempting non-fix

Raising CONFIG_IEEE802154_RX_BUFFER_SIZE makes the sniffer survive 100 frames instead of 20. It feels like progress and it is not — a leak is a leak, and all you have bought is a longer wait before the same silence.

What is still wrong

This sketch no longer dies, but it is still doing something it should not: printing from inside the callback. On a busy channel it drops frames continuously, silently, with no counter to tell you. That is chapter 5.

It is worth being clear that the fix was still worth having on its own. A sniffer that drops some frames is useful; a sniffer that stops after 20 is not.
