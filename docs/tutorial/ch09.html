Chapter 9

Transmitting, and getting acknowledged

Receiving is forgiving — a frame you fail to parse is a frame you ignore. Transmitting is not. Get one header field wrong and the receiver's hardware filter drops your frame before any software sees it, and you get no error at all. Just silence.

Sketch sketches/ch09_transmit/ch09_transmit.ino

The ACK is the whole point

Because failure is silent, you need one honest signal that the other end accepted your frame. That signal is the acknowledgment.

The receiving MAC sends it automatically, in hardware, and only if your frame passed CRC and passed its address filter. So an ACK is not a courtesy — it is proof that every field in your header was right. One bit of feedback tests the lot.

Two ways transmit differs from receive

The length byte includes an FCS you do not write

buf[0] is the PSDU length including the two-byte FCS, and the hardware appends a real CRC. So for 12 bytes of header and payload you set buf[0] = 14 and write 12 bytes:

buf[0] = (uint8_t)((p - (buf + 1)) + 2);   // +2 for the FCS

Writing the payload length there instead of the PSDU length is the classic off-by-two in this API, and it produces a frame nobody answers.

Promiscuous mode must be off

Promiscuous disables address filtering and automatic ACKs. A promiscuous node never replies to anyone and is never replied to. A sniffer and a participant are different roles, so this sketch configures itself as a real member of the PAN:

esp_ieee802154_set_channel(CHANNEL);
esp_ieee802154_set_panid(PAN_ID);
esp_ieee802154_set_short_address(MY_ADDR);
esp_ieee802154_set_promiscuous(false);
esp_ieee802154_set_rx_when_idle(true);   // required, to hear the ACK
esp_ieee802154_receive();

Those are the calls chapters 3–8 could ignore. The rx_when_idle line is not optional here: the ACK arrives well under a millisecond after your frame goes out, and the radio has to be back in receive by then.

Building the frame

Chapter 7 in reverse, little-endian throughout:

p = put16(p, 0x8861);     // Data, ACK req, PAN compressed, short/short
*p++ = sequence;
p = put16(p, PAN_ID);     // destination PAN
p = put16(p, DEST_ADDR);  // destination short address
p = put16(p, MY_ADDR);    // source short address, no source PAN
memcpy(p, payload, plen);

The source PAN is omitted because the compression bit in the FCF says it is. Set that bit and then write the field anyway and everything downstream shifts by two bytes.

Sending

esp_err_t err = esp_ieee802154_transmit(frame, true);

The second argument is CCA — clear channel assessment. With true the radio listens first and backs off if the channel is busy, which is the polite behaviour and the right default on a shared band. false transmits immediately regardless.

A non-ESP_OK return is a local rejection: the frame never reached the air. Everything else is reported asynchronously through two callbacks you define by name, exactly like the receive one.

CallbackMeans
esp_ieee802154_transmit_done with ack != NULL It arrived and the other end accepted it. This is the result you want.
esp_ieee802154_transmit_done with ack == NULL It went out and nothing answered. Nobody at that address, or they did not hear you.
esp_ieee802154_transmit_failed The radio gave up. Usually CCA failure (channel busy every attempt) or an ACK timeout after its retries.
The ACK is a receive buffer too

The acknowledgment arrives in one of the same pool of buffers from chapter 4, so it has to be returned:

esp_ieee802154_receive_handle_done((uint8_t *)ack);

Leak these and you hit the twenty-frame wall again — just more slowly, and in a transmit path where you are not looking for it.

Debugging a frame nobody accepts

The useful move is to sniff your own transmission. Put chapter 7 on a second C6 on the same channel, and the question splits in two:

  • Your frame does not appear there at all — the problem is radio configuration. Channel first, then whether transmit() is returning ESP_OK.
  • It appears, but the real device ignores it — the problem is in the header fields, and chapter 7's parser is already printing them back to you. Check PAN ID, then destination address, then whether buf[0] is the PSDU length rather than the payload length.

Remember that the chapter 7 sniffer is promiscuous, so it will show you the frame but will never ACK it. For a real ACK you need a genuine member of the PAN.
