Chapter 5

Getting out of the callback

The receive callback runs in interrupt context. Chapters 3 and 4 print from inside it, which is the worst thing you can do there, and the cost is invisible — dropped frames leave no trace.

Sketch sketches/ch05_ring_buffer/ch05_ring_buffer.ino

The arithmetic

esp_ieee802154_receive_done() is not a task. While you are inside it the radio is not being serviced, so every microsecond spent there is a chance to miss the next frame.

Printing is catastrophically slow by that standard. A 14-byte hex dump is about 42 characters, and at 115200 baud each character is roughly 87 µs:

42 chars × 87 µs ≈ 3.6 ms

An 802.15.4 frame of that size occupies the air for well under a millisecond. So the handler for one frame blocks for several times the duration of the next one. On a quiet channel you never notice; on a busy one chapters 3 and 4 are dropping frames constantly and cheerfully reporting nothing wrong.

Copy out, parse later

The callback's whole job becomes: copy the bytes somewhere safe, and return.

uint8_t len = frame[0];
if (len > MAX_FRAME_LEN) len = MAX_FRAME_LEN;   // clamp before the memcpy

uint8_t next = (q_head + 1) % QUEUE_LEN;
if (next == q_tail) {
  dropped++;                 // queue full
} else {
  queue[q_head].len  = len;
  queue[q_head].rssi = frame_info ? frame_info->rssi : 0;
  memcpy(queue[q_head].data, &frame[1], len);
  q_head = next;
}
esp_ieee802154_receive_handle_done(frame);

That clamp is not decoration. frame[0] arrives off the air, and a corrupt length would run straight off the end of the destination array. It should never fire in normal operation, which is precisely why it has to be there.

Why no lock is needed

This is a single-producer, single-consumer ring buffer, and that structure is what makes it safe without disabling interrupts or taking a mutex:

  • the callback only ever writes q_head
  • loop() only ever writes q_tail
  • neither one writes the other's index

Both indices are volatile so the compiler cannot hoist them out of the drain loop and spin on a stale value forever.

One ordering detail in drainQueue() matters more than it looks:

// print the frame fully, THEN release the slot
q_tail = (q_tail + 1) % QUEUE_LEN;

Advancing q_tail first would let the callback overwrite the slot while loop() is still halfway through printing it, producing a torn frame — half of one packet, half of another. That is a bug you will never reproduce on demand, so it is worth getting right by construction.

Full means drop

When the queue fills, the sketch discards the new frame rather than overwriting the oldest. Both choices lose data; only one of them can corrupt a frame that is being printed. Losing the newest frame is recoverable and countable:

-- 1284 received, 0 dropped (queue full)
Try it

Set QUEUE_LEN to 2 and point the sketch at a busy channel. The dropped counter starts climbing, and the trade-off becomes concrete: the queue only has to be long enough to cover one pass of loop().

A better place for RSSI

The sketch now reads signal strength from frame_info rather than from the frame bytes:

queue[q_head].rssi = frame_info ? frame_info->rssi : 0;
queue[q_head].lqi  = frame_info ? frame_info->lqi  : 0;

That second argument to the callback has been there since chapter 3, unused. It carries the receiver's own measurements of the frame. Chapter 8 is about why reading them from here, rather than from the end of the packet, is not merely a style preference.
